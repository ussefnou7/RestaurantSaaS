## Findings, most severe first

### F1 — `updateSettings` silently resets `maxAgeDays` to 0 on every save from the shipped UI, switching the fresh-track alert off

**SUSPECTED** (both halves read directly; not driven end-to-end over HTTP — see caveat).

**What is wrong.** `StockBalanceService.updateSettings` writes `maxAgeDays` unconditionally from the
request, and `nz(null)` is `0`, which is D113's "unconfigured" sentinel — so any client that omits
the field wipes it.

**Where.**
- [StockBalanceService.java:206](src/main/java/com/smart/restaurant_saas/inventory/core/StockBalanceService.java:206)
  — `balance.setMaxAgeDays(nz(request.getMaxAgeDays()));`, no null guard.
- [StockBalanceService.java:398](src/main/java/com/smart/restaurant_saas/inventory/core/StockBalanceService.java:398)
  — `nz(Integer)` returns `0` for null.
- Caller that omits it: `restaurant-saas-web/src/pages/inventory/WarehouseStocksPanel.tsx:293-295`
  — `updateStockSettings(...)` sends `{ minimumQuantity }` only. `maxAgeDays` appears nowhere in the
  web repo (`grep -rn maxAgeDays src/` → no hits).

**Failure scenario.** Tenant sets `maxAgeDays = 3` for (chicken, Branch A) — today only reachable by
direct API call, since no UI writes it. A storekeeper later opens the warehouse-stock row and edits
the minimum quantity from 10 to 12. The PUT body is `{"minimumQuantity": 12}`. `maxAgeDays` becomes
`0`. Every batch of that pair now returns `daysRemaining = null` and renders `—`; the fresh track for
that material is off, with no error, no audit trail and nothing in the response to indicate the
field was touched.

**Why this is not "mirrors `minimumQuantity` exactly" as decided.** It does mirror it — that is the
mechanism of the bug. `minimumQuantity`'s full-replace semantics are harmless because the only
client that writes the endpoint always sends it. `maxAgeDays` has no client that sends it, so the
same semantics produce a pure destructive write. The same pass got this right on the other new
field: [MaterialService.java:93-94](src/main/java/com/smart/restaurant_saas/inventory/service/setup/MaterialService.java:93)
guards `expiryTracked` with `if (request.getExpiryTracked() != null)`. The two new booleans/ints
added by one decision use opposite policies for partial payloads, and only the guarded one is safe.

*(`maximumQuantity` is nulled by the same write. That is pre-existing and out of scope; it is
mentioned only because the fix is one path, not one field — same note O43 already makes.)*

**Caveat on the label.** The only step not exercised is Jackson leaving an absent JSON property
null, which is its default. Both code halves were read in full and the overwrite is unconditional
with no branch. Treat as near-certain; it is labelled SUSPECTED only because no request was issued.

### F2 — Physical Count numbering contention widened from per-warehouse-per-day to per-tenant-per-year, and the counter row is held for the whole create transaction

**CONFIRMED** for the lock behaviour and the timeout (reproduced against the real `document_sequence`
table with the project's configured `lock_timeout`). **CONFIRMED by code** for the 500 mapping.

**What is wrong.** `DocumentSequenceService.next` is `@Transactional` with default propagation, so it
joins the caller's `create` transaction and the `ON CONFLICT DO UPDATE` row lock is held until that
transaction commits — while the caller does the rest of its work. For Physical Count this is a
regression, because the counter scope also widened: the deleted
`PhysicalCountCodeSequenceService.next` keyed on `(tenant_id, warehouse_id, scheduled_date)`, and
`DocumentSequenceService.next` keys on `(tenant_id, PHYSICAL_COUNT, year)`.

**Where.**
- [DocumentSequenceService.java:39-50](src/main/java/com/smart/restaurant_saas/inventory/core/DocumentSequenceService.java:39)
  — `@Transactional` (REQUIRED), no `REQUIRES_NEW`.
- [PhysicalCountService.java:254-262](src/main/java/com/smart/restaurant_saas/inventory/core/PhysicalCountService.java:254)
  — code allocated first, then a loop calling `buildLine` (one `resolveMaterial` query per material,
  [PhysicalCountService.java:919-930](src/main/java/com/smart/restaurant_saas/inventory/core/PhysicalCountService.java:919)),
  then `saveAndFlush`. All of it under the lock.
- Old scope: `git show 7f0efb3:src/main/java/com/smart/restaurant_saas/inventory/physicalcount/PhysicalCountCodeSequenceService.java`
  and `V38__physical_count_code_sequence.sql:8`.
- [GlobalExceptionHandler.java:85-91](src/main/java/com/smart/restaurant_saas/common/GlobalExceptionHandler.java:85)
  — no handler for `DataAccessException`/`CannotAcquireLockException`; it falls to the catch-all
  `Exception` handler → HTTP 500 `INTERNAL_ERROR`.

**Reproduction (run during this review, on `restaurant_saas_test`).** Session A opens a transaction,
runs the allocator's exact upsert for `(999001, PURCHASE_INVOICE, 2026)`, and holds. Session B, with
`SET lock_timeout = 5000` — the value
`src/test/resources/application.yml` and D92 put on every pooled connection — runs the same upsert
and fails:

```
ERROR:  canceling statement due to lock timeout
CONTEXT:  while inserting index tuple (0,1) in relation "document_sequence"
```

**Failure scenario.** Two supervisors in one tenant start a physical count at the same moment, in two
different warehouses, each over ~400 materials. Under the old scheme they touched two different
counter rows and never interacted. Now the first allocates `PC/26/00000N` and holds that row through
~400 material lookups plus the line insert; the second blocks on the same row and, if the first takes
longer than 5 s, is cancelled by `lock_timeout`. The user sees HTTP 500 `INTERNAL_ERROR` on "create
count" — the same unhelpful shape O43 records for the settings write, and for the same underlying
reason (a recoverable concurrency conflict never reaching a structured `AppException`).

**Why the existing test cannot catch this.** `DocumentSequenceIntegrationTest` says so itself, in its
own javadoc: *"this means Spring's `@Transactional` proxy is absent and each allocation autocommits;
the atomicity under test belongs to the SQL upsert, not to the proxy"*
([DocumentSequenceIntegrationTest.java:24-38](src/test/java/com/smart/restaurant_saas/inventory/core/DocumentSequenceIntegrationTest.java:24)).
The eight-thread test constructs the service directly, so every allocation commits immediately and
no lock is ever held across other work. D112's build note reports this as *"concurrency is exercised
rather than argued"* — accurate about the upsert, and silent about the only concurrency shape that
production actually has. The 1–8 result is real; it does not cover the production path.

**Scope note.** For Purchase Invoice, Waste and Purchase Return the transaction after allocation is
short (one header save), so contention there is narrow and this is not a regression — the old
`invoice_sequence` counter had the same `(tenant, year, doc_type)` scope. Physical Count is the
regression.

### F8 — a live, public, uncalled document-number generator survives the cutover, carrying F7's race

**CONFIRMED** (no production callers; race shape read, not exercised).

**What is wrong.** `TenantSequenceService.generateDocumentNumber` is the retired document-number
entry point that `InvoiceSequenceService` delegated to. `InvoiceSequenceService` is deleted;
`generateDocumentNumber` is not, and now has zero production callers — `grep -rn
generateDocumentNumber src/` returns only `TenantSequenceServiceTest`.

**Where.**
[TenantSequenceService.java:26-32](src/main/java/com/smart/restaurant_saas/common/sequence/TenantSequenceService.java:26).
It is also the last string-assembled document number in the tree (`String.format("%04d", next)` at
line 31 — a full `%0Nd`/concatenation sweep of `src/main` finds nothing else).

**Failure scenario, two of them.**
1. `increment` does `findForUpdate(...).orElseGet(newCounter)`. `@Lock(PESSIMISTIC_WRITE)`
   ([TenantSequenceCounterRepository.java:12](src/main/java/com/smart/restaurant_saas/common/sequence/TenantSequenceCounterRepository.java:12))
   locks a row that exists; on the **first** document of a new (tenant, year, type) there is no row
   to lock, two threads both build `lastSeq = 1`, and the unique constraint rejects one with no
   recovery path. That is F7, verbatim, still resident. D112's build note says F7 is *"retired along
   with the service"* — the service that wrapped it is retired; the racing method is not.
2. It uses `Year.now()` — the **server's** year, not the tenant's. Its next caller reintroduces
   D101's bug in the one field D112's own text calls out as the trap
   ([DECISIONS.md:3184-3187](docs/DECISIONS.md:3184)).
   `generateEntityCode`, the live D75 path, deliberately uses the `year = 0` bucket and is unaffected.

Note this is genuinely latent — nothing calls it today. It is listed because §1 named exactly this
shape ("a retired service with no callers is F7's race waiting for its next caller") and, on the
sweep, this is where that shape actually is.

   [PurchaseInvoiceService.java:112](src/main/java/com/smart/restaurant_saas/inventory/core/PurchaseInvoiceService.java:112),

   `DocumentSequenceIntegrationTest.aDiscardedNumberLeavesAGapThatIsNotReused` pins that.
   `uncompleteSucceedsFromCompletePreservesInvoiceNumberAndEnablesLineEditing` pins the no-realloc
   side. The end-to-end create→failed-post sequence was **not driven as a single scenario**; the
   conclusion is composed from those verified parts.
3. **The guard still fires.** `postRejectsTrackedLineWithoutExpiryDateUsingStructuredLineParams`,
   `trackedMaterialMayBeSavedOnDraftLineWithoutExpiryDate` and
   `postCopiesLineExpiryDateIntoLedgerCommand` are all present in the current
