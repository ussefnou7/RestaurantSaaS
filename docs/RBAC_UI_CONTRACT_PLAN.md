# RBAC UI contract — plan (Claude ↔ Gemini)

Status: proposed, not shipped. Drafted 2026-09-21.

Supersedes the frontend sections of [UI_PERMISSIONS_PLAN.md](UI_PERMISSIONS_PLAN.md), which
described the same goal before the backend contract existed. That file's "decisions still
required" are answered here.

## Goal

The frontend must know, without asking the server per widget, whether the current user may open a
screen or press a button — so a forbidden action is never rendered as a live control and its
endpoint is never called. The backend keeps enforcing every request unchanged, so a call made
outside the UI still fails.

Two layers, never one:

- **Frontend = usability.** Hide or disable what the user cannot do. Saves the round trip.
- **Backend = authority.** `@PreAuthorize` stays exactly as it is. No caching, no JWT-embedded
  permissions, no relaxation. A direct API call by an unauthorized user must still be rejected.

This split is not defense in depth as an afterthought; the frontend layer is advisory and may be
stale by design (see *Freshness* below). Only the backend answer is binding.

## What already exists — do not rebuild

- `AuthService.buildAuthUserResponse` already loads the user's active direct permission codes into
  `AuthUserResponse.permissions`. Both login and `GET /api/auth/me` return them.
  ([AuthService.java:184](../src/main/java/com/smart/restaurant_saas/auth/service/AuthService.java:184))
- The web app already declares `AuthUser.permissions` and persists the login response.
- 232 `@PreAuthorize` gates exist across controllers, covering 56 distinct permission codes.
- All 56 gated codes are present in the permission seed — there are no always-deny gates.

No new endpoint, no new permission table, and no new role model is needed.

## The missing piece

There is no machine-readable map from a permission code to the screens and controls it governs.
The frontend currently holds four hand-written `src/utils/*Access.ts` files that drifted from the
backend. Auditing them surfaced four concrete defects, listed under *Defects to fix* below.

## Deliverable 1 — the generated manifest (Claude / backend) — ✅ shipped

`docs/contracts/permission-manifest.json`, regenerated by
`src/test/java/com/smart/restaurant_saas/rbac/contract/PermissionManifestTest.java`, never
hand-edited. Runs in ~1s with no Spring context and no database.

Current output: **56 permission codes over 211 endpoint bindings**, 3 role rules
(`isSysAdmin` 20 endpoints, `isOwnerOrBranchManager` 16, `isOwner` 3), and 11 login-only endpoints.

Reflection paid for itself immediately: eight controllers carry a **class-level** `@PreAuthorize`
that every method inherits. Grepping annotations finds 8 gates there; the scanner correctly
expands them to 39 endpoints. A hand-written contract would have been wrong on all four HR
controllers from day one.

Generated by a Spring Boot test that walks `RequestMappingHandlerMapping` and reads the merged
`@PreAuthorize` off each handler method. Resolving through the handler mapping — rather than
grepping source — gives the exact HTTP method and full path with the class-level
`@RequestMapping` prefix already applied, and it cannot silently miss a gate.

The four expression shapes in the codebase are uniform enough to parse exhaustively:

| Shape | Count | Manifest treatment |
|---|---|---|
| `isSysAdmin() or hasPermission('X')` | most | endpoint requires `X` |
| `hasPermission('X')` | 2 | endpoint requires `X` (identical — `hasPermission` already bypasses sysadmin) |
| `isSysAdmin()` / `isOwner()` / `isOwnerOrBranchManager()` | 11 | endpoint requires a **role**, not a permission |
| `isAuthenticated()` | 5 | no gate beyond login |

Any expression the parser does not recognize must **fail the test**, not be skipped. That is what
keeps the manifest honest as Codex adds controllers.

```json
{
  "permissions": [
    {
      "code": "EXPENSES_VOID",
      "module": "expense",
      "type": "ACTION",
      "endpoints": [
        { "method": "POST", "path": "/api/expenses/{id}/void", "handler": "ExpenseController.voidExpense" }
      ]
    }
  ],
  "roleGates": [
    { "rule": "isOwnerOrBranchManager", "endpoints": [ { "method": "GET", "path": "/api/hr/leaves" } ] }
  ],
  "seededButUnenforced": ["SHIFTS_VIEW_VARIANCE"]
}
```

`seededButUnenforced` matters: a code can be seeded and meaningful to the UI without gating any
endpoint. `SHIFTS_VIEW_VARIANCE` is exactly this — it hides a *column*, not a route. Gemini may
gate display on these, but must never assume the backend withholds the underlying field.

## Deliverable 2 — the screen map (Gemini / frontend)

`restaurant-saas-web/src/access/screen-map.ts`, hand-authored, typed, the single place any gating
decision is written down. One entry per route and per mutating control.

```ts
export const SCREEN_MAP = {
  'expenses.list': {
    route: '/expenses',
    requires: 'EXPENSES_VIEW',
    actions: {
      create: 'EXPENSES_CREATE',
      void:   'EXPENSES_VOID',
    },
  },
} as const
```

Rules for authoring it:

- The `requires` code for a control must be the code the *actual endpoint that control calls*
  is gated by — read it off the manifest, never guess it from the name. `PRODUCTS_UPDATE` and
  `PRODUCTS_CHANGE_STATUS` are separate gates on the same screen, for example.
- A route whose backend gate is a **role** (`roleGates` in the manifest) is gated on `roleCode`.
  Do not invent a permission code for it — the HR module is the live case.
- A control with no manifest entry is a bug in one side or the other. Resolve it; do not default
  to visible.

## Deliverable 3 — the drift test (Claude)

A CI test asserting every code referenced by `screen-map.ts` appears in the manifest as either a
gated permission, a declared role gate, or `seededButUnenforced`. Without this the two files
diverge within weeks, which is precisely how the current `*Access.ts` files got into the state
described below.

## Deliverable 4 — the frontend wiring (Gemini)

1. One `AuthContext` holding the reactive session. Today `*Access.ts` helpers read
   `localStorage` on every call, so removing a permission does not re-render anything.
2. One `can(code)` helper, with the backend's **`SYS_ADMIN`-only** bypass — see the defect below.
3. `ProtectedRoute` gains a `requires` prop and enforces it. Today it checks only for the presence
   of a token ([ProtectedRoute.tsx](../../restaurant-saas-web/src/guards/ProtectedRoute.tsx)), so
   typing a URL reaches any screen.
4. Navigation links, route guards and action buttons all consume `SCREEN_MAP` — no inline string
   literals at call sites.
5. Delete the four `*Access.ts` files once their call sites are migrated.

## Progress — 2026-09-22

All four deliverables are in. Shipped:

- **Manifest generator** — `PermissionManifestTest`, ~1s, no Spring context, no database.
- **Typed contract** — `src/access/permissions.generated.ts`, synced by `npm run sync:permissions`.
- **Reactive session** — `AuthSessionProvider`, `useAuthSession`, `useAccess`, `can.ts`.
- **Screen map** — `src/access/screen-map.ts` with per-entry `onDenied`, resolved by
  `screenAccess.ts`, enforced by `guards/ScreenGuard.tsx` on 13 module routes and read by
  `ClientLayout` for the sidebar. Nav and routes read the same entry, so they cannot disagree.
- **Access-denied surface** — `components/AccessDenied.tsx` plus `access.*` strings in en and ar.
- All seven `utils/*Access.ts` rewritten on top of `can.ts`, fixing every defect below without
  touching their 48 call sites. HR became a grantable permission (D136).

### The drift test is the type system

`SCREEN_MAP.requires` is typed as `PermissionCode`, generated from the backend's gates. A code the
backend does not enforce does not compile. Verified by substituting `EXPENSES_DESTROY` for
`EXPENSES_VOID`: `tsc` fails with `TS2322` naming the exact line. This is stronger than the runtime
assertion originally planned as Deliverable 3, and it is the exact failure mode that produced the
four defects below — every one of them was an invented code that nothing rejected.

### Verified in the browser — 2026-09-22

Driven as `sakka11` (role `HR_MANAGER`, tenant `f7am`), who holds expenses, shifts, orders,
`PRODUCTS_VIEW` and `TABLES_VIEW`, and notably **not** `HR_MANAGE`.

| Check | Result |
|---|---|
| Sidebar | Only Main, Expenses, Management. Sales, Inventory, Assets, Purchase and **HR** hidden. |
| Denied routes by direct URL | `/hr`, `/users`, `/devices`, `/inventory`, `/assets`, `/purchase`, `/sales`, `/branches` — all render the access-denied page, none blank. |
| Allowed routes | `/expenses`, `/shifts`, `/menu`, `/orders`, `/tables` — all render their real screen. |
| Backend agreement | `GET /api/hr/leave-requests`, `/api/hr/employees`, `/api/users`, `/api/devices` → **403**. `/api/expenses`, `/api/shifts` → **200**. Exactly what the UI showed. |
| Arabic / RTL | `dir=rtl`, denied screen and sidebar render the `ar` strings. |

The HR row is D136 working end to end: an `HR_MANAGER` without the `HR_MANAGE` grant is refused by
the server and never shown the module. Under the old `hrAccess.ts`, that role was hardcoded into
`PAYROLL_ROLES`, so the UI offered payroll actions the backend had always rejected.

It also settles the `ScreenGuard` risk: eleven of the thirteen guarded routes are children-only, so
the guard renders through `Outlet`. Every one of them still renders its screen.

### Known gap — action-level gating is defined but not consumed

`SCREEN_MAP.actions` is authored and resolvable through `canDoAction`, but the pages have not been
migrated to it. Confirmed live: on `/menu/products` the **Add product** button is enabled for a user
without `PRODUCTS_CREATE`, whose `POST /api/products` the backend gates. The menu page never gated
that button — there was no `menuAccess.ts` — so this is a pre-existing gap the new map can now
close, not a regression.

Remaining work, in order:

1. Consume `canDoAction` at the action call sites, starting with menu, expenses and shifts.
2. Migrate the 48 `*Access.ts` call sites to `useAccess()`. The shims are correct but read
   `localStorage`, so a mid-session permission change does not re-render until navigation.

## Defects to fix — found while auditing, independent of the new plumbing

1. **`OWNER` sees buttons that return 403.** `shiftAccess.ts` and `deviceAccess.ts` bypass gates
   for `OWNER`, but `SecurityService.hasPermission` bypasses for `SYS_ADMIN` only
   ([SecurityService.java:52](../src/main/java/com/smart/restaurant_saas/auth/service/SecurityService.java:52)).
   Decided: **fix the frontend**, matching D36 and the "role is a gate, not a permission source"
   invariant. Owners hold real grants or they see nothing. Verify the role seed actually gives
   `OWNER` the grants it needs before shipping, or existing owners lose screens.
2. **`SHIFTS_MANAGE` is dead.** Referenced in `shiftAccess.ts`; neither seeded nor gated anywhere.
   The `canCloseShift` check that ORs it in is therefore partly meaningless.
3. **`canCloseShift` ORs in `SHIFTS_VIEW`.** Being able to *see* a shift grants the close button.
   The backend gates close separately. Straightforward privilege confusion.
4. **HR permission codes the backend ignores.** The frontend checks `HR_LEAVES_CREATE`,
   `HR_LEAVE_TYPES_*` and `HR_SALARY_ADDITIONS_*`; those endpoints are gated by the
   `isOwnerOrBranchManager()` role rule instead — applied at **class level** on
   `LeaveRequestController`, `LeaveBalanceController`, `SalaryController` and
   `SalaryAdjustmentController`, so it covers all 16 of their endpoints. Every HR permission the
   frontend tests is inert. The two sides disagree in both directions.
5. **Media endpoints have no permission gate at all.** `POST /api/media/uploads`,
   `DELETE /api/media/links/{linkId}` and the read endpoints sit in `authenticatedOnly` — any
   logged-in user of any tenant role can upload or delete a media link. This may be deliberate,
   since media is shared across modules, but it is not written down anywhere. Out of scope for
   this plan; raised because the manifest made it visible. Needs its own decision.

## Freshness

Permissions are read at login and on `/me`. Refresh `/me` on app focus, and after any permission
edit affecting the current user. A change made in another administrator's session will not appear
in a continuously open tab until one of those events — accepted, because the backend rejects the
request regardless. No polling, no push.

## Explicitly out of scope

No JWT-embedded permissions and no server-side permission cache. `hasPermission` stays a live
per-request read. D36 states this directly, and the `isSysAdmin` incident recorded in
`SecurityService`'s class comment is what happens when an authorization answer is served from a
login-time snapshot. The savings sought here are frontend round trips, not database reads.

## Sequencing

Deliverable 1 must land before 2. Gemini cannot author the screen map correctly without the
manifest — the four defects above are all instances of guessing a gate rather than reading it.

Suggested first slice: expenses and shifts. Both have a full create/edit/void gate set, and shifts
exercises the role-gate and `seededButUnenforced` cases that the naive design misses.

## Presentation — Gemini's call, declared per entry

How a forbidden surface looks is **not** fixed globally here. It differs per surface: an action
button is best disabled with a reason, a whole screen usually just disappears with nothing written
at all, a workflow step is different again. Picking one rule for all of them would be wrong.

So presentation is a field on each `SCREEN_MAP` entry, authored by Gemini, so that changing how
something behaves is a one-line edit in one file rather than a hunt through components:

```ts
'expenses.list': {
  route: '/expenses',
  requires: 'EXPENSES_VIEW',
  onDenied: 'hide',                 // hide | disable | deny-screen
  actions: {
    create: { requires: 'EXPENSES_CREATE', onDenied: 'hide' },
    void:   { requires: 'EXPENSES_VOID',   onDenied: 'disable' },
  },
},
```

Two constraints on that freedom, both correctness rather than taste:

- **`hide` on a route hides the link, not the route.** A URL is always typeable, so the route
  itself still needs a real deny — an access-denied screen, or a redirect. Not a blank page, and
  never a screen that renders and fires its requests anyway. This is the only part of presentation
  the drift test should check.
- **`disable` is styling**, trivially removed in devtools. That is expected and is why the backend
  gate is the binding one. No client-side hardening to compensate.

If a denied surface shows text, the manifest can carry `name_ar` / `name_en` from the `permissions`
table so Gemini reuses the real permission names instead of writing new strings. Offered, not
required — most surfaces will not need any text.
